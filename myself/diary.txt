一、整体架构与原理
    采用分层架构设计（10层）。每层SPI机制实现扩展，URL作为统一的信息载体。
    Dubbo 3.x 引入FrameworkModel -> ApplicationModel -> ModuleModel三层Scope模型,每个层级支持独立的SPI上下文，支持多应用隔离部署

    1.1 分层架构
                   层级       主要职责                     核心类                               源码路径
        Business| service   业务接口和实现         @DubboService @DubboReference                dubbo-config
             RPC| Config    配置解析与组装         ServiceConfig,ReferenceConfig,DubboBootstrap dubbo-config
                  Proxy    Invoker<->代理对象转化 ProxyFactory,JavassistProxyFactory            dubbo-rpc
                  Registry  服务注册/发现/订阅     Registry,FailbackRegistry,RegistryProtocol   dubbo-registry
                  Cluster  容错/路由/负责均衡      Cluster,Directory,LoadBalance, RouterChain   dubbo-cluster
                  --Monitor 监控                Monitor,MonitorFactory, MonitorFactory        dubbo-metrics
                  Protocol RPC协议暴露与引用      DubboProtocol,Triple协议，InjvmProtocol        dubbo-rpc
        Remoting| Exchange 请求-响应模型封装      Exchangers,HeaderExchangeServer/Client        dubbo-remoting
                  Transport 网络传输层(NIO)      Transporters,NettyServer,NettyClient          dubbo-remoting
                  Serialize 序列化协议           Serialization,Hessian2Serialization,Fastjson2 dubbo-serialization

    1.2 SPI机制核心 - ExtensionLoader
        Dubbo SPI是整个框架的基石，支持Activate激活过滤(IOC),自适应扩展(Adaptive),Wrapper包装器(AOP)三个特性
        SPI核心方法：
            getExtensionLoader(Class)               三层Scope获取和创建类型的ExtensionLoader静态方法
            getExtension(name)                      按名后去扩展实例(带双重检查锁机制)
            createExtension(name,wrap)              SPI核心创建：加载类->反射实例化->IOC注入-Wrapper包装
            getAdaptiveExtension()                  自适应扩展(动态字节码生成或@Adaptive注解)
            getActivateExtension(url, key, group)   基于@Activate条件激活(Filter链核心)
        createExtension创建流程
            getExtensionClass -> 反射实例化 -> postProcessBeforeInitialization -> injectExtension -> postProcessAfterInitialization -> Wrapper(是:cacheWrapperClasses层层包装，否:跳过)->initExtension（Lifecycle初始化）
        SPI缓存机制
            ExtensionLoader使用多种缓存保证新能，锁粒度控制到Holder级别：cachedClasses, cacheInstances, cacheAdaptiveInstance, extensionInstances

        SPI配置文件位置
            SPI配置文件位于各模块的META-INF/dubbo/internal/目录下，文件名为接口权限定名

        Wrapper AOP机制：
            Protocol的SPI包装链为：ListenerWrapper->SerializationWrapper->SecurityWrapper->InvokerCountWrapper->真实DubboProtocol
            export/refer/destroy都会逐层穿透，类似AOP环绕通知

    1.3 三级Scope模型
        Dubbo3.x引入了三级Scope模型，替代2.x的全局单利设计，支持多应用隔离
        FrameworkModel（框架级，JVM内单利） -> ApplicationModel(应用级别，多应用隔离) -> ModuleModel（模块级，同一个应用多模块）
        每个应用都有独立的ExtensionRepository仓库，SPI扩展实例在Scope内单利、Scope间隔离。使同一个JVM内可以部署多个Dubbo应用而不互相干扰
        JVM -- 虚拟机层 目的：Dubbo框架之间完全隔离(端口不能复用)
        Dubbo Framework -- 框架层 目的：将需要全局缓存的进行（端口、序列化等）
        Application -- 应用层 目的：隔离应用之间的信息，包括注册中心，配置中心，元数据中心
        Services（Module）-- 模块层 目的：提供热加载能力，可以按ClassLoader, Spring Context进行隔离上下文

        Model（作用域）+ Factory(Bean工厂) + Director(管理器) + Accessor（访问入口）

        ExtensionDirector：才是真正的SPI管理中心

        ApplicationModel:
            dubbo.properties
            dubbo-migration.yaml: 控制服务消费者在接口级地址(Interface-Level Discovery)和应用级地址(Application-Level Discovery)之间如何选择，实现平滑迁移

        说明：每级都要自己的 Scope, beanFactory, environment, configManager
             每级Model启动通过ScopeModelInitializer进行初始化配置


二、启动架构原理与源码
    启动入口统一在DubboBoostrap,内部委托给ApplicationDeployer(DefaultApplicationDeployer)和ModuleDeployer(DefaultModuleDeployer), 通过三级Scope模型管理生命周期
    dubbo-config: 启动配置管理包
        dubbo-config-api: dubbo配置及启动
        dubbo-config-spring: dubbo 与 Spring的集成
            dubbo-common: config, metadata, rpc

    1、DubboBootstrap(ApplicationDeployer+操作):
        initialize(): ApplicationDeployer.initialize()
                 应用初始化监听器,注册DubboShutdownHook,启动配置中心(如果没有配置注册中心),加载应用配置，初始化ModuleDeployer->启动元数据中心
                 initModuleDeployers: module.getDeployer().initialize()
                    ModuleDeployer:
                            initialize(): 模块初始化，加载配置，后台启动设置、异步导出、异步引用设置
        start(): applicationDeployer.start()
                 initialize(初始化幂等)->doStart()(module.start)->
                 module.start(): exportServices(), referServices(), registerServices()
                    ModuleDeployer:
                        startSync(): 标记启动中发布事件，初始化(幂等)，导出服务，引用端初始化，
                                        注册服务(Registry), referenceCheck(引用端检查)，
        await(): 阻塞等待，配合start(true)等待启动完成
        stop()/destroy()：优雅停机，委托applicationModel.destroy()

    2、Provider启动
        AbstractConfig: 配置解析\属性绑定、参数转换、校验和URL参数生成等通用能力
        ServiceConfig.export() -> 确保模块启动
            -> doExportUrls() 遍历所有Protocol
            -> doExportUrlsFor1Protocol() 构建ServiceUrl,处理执行器
            -> exportUrl() scope:local + remote
                ->exportLocal()
                ->exportRemote()
                    -> doExportUrl: ref-> AbstractProxyInvoker // Wrapper实现避免反射提高服务端性能（静态大力直接调用）
                        ->ProtocolSPI.export(Invoker)
            -> exported(): 导出完成之后的操作,Dubbo3服务元数据处理

    3、Consumer启动

        ReferenceConfig.get()->createProxy()->createInvoker()+proxyFactory.getProxy()
        ClusterInvoker: 真正执行RPC
            invoke()->Directory.list()->Router->LoadBalancer.select()->Invoker.invoke()-> 失败?->Retry?->返回
        应用级和接口级注册切换：
            ServiceDiscoveryMigrationInvoker创建：RegistryProtocolListener->MigrationRuleListener->MigrationRuleHandler.refreshInvoker创建
            Directory：DynamicDirectory.refreshInvoker: invocation->Invokers
                       最终调用协议的refer真是远程调用Invoker

    4、protocol
        整体过程：Protocol$Adaptive->ProtocolFilterWrapper->ProtocolListenerWrapper->RegistryProtocol->Protocol$Adaptive->ProtocolFilterWrapper->ProtocolListenerWrapper->Dubbo/Triple/RestProtocol->ExchangeServer->NettyServer
        当获取Adaptive扩展时，如果没有实现，会生成一个Protocol$Adaptive扩展类
        RegistryProtocol：接收registry://风格URL把服务暴露和引用委托给真是协议，同时完成向注册中心的注册、订阅与配置覆盖
        Cluster：是容错层，把多个Provider（Invoker）包装成一个具有集群能力的Invoker,对上层透明底提供负载均衡，容错，重试，路由等能力
        DubboProtocol:
            DubboExport
            DubboInvoker

三、关闭原理与源码
    Dubbo3.4采用分阶段优雅停机策略，确保在途请求处理完成后释放资源，由ApplicationModel的生命周期驱动
    preDestroy: onStoping(标记状态)， offline()服务下线，unregisterServiceInstance（）注销元数据，停止接收新请求
    postDestroy: 反暴露服务，销户消费者，关闭注册中心连接，关闭线程池，销毁框架



五、客户端请求处理
    负载均衡机制：LoadBalance是SPI接口，默认实现random（加权随机），支持服务预热(warmup)
        random（加权随机），roundrobin(加权轮询)，leatactive（最少活跃数），shortestresonse（最短响应时间），consisthash（一致性hash）
    路由体系：RouterChain维护mainChain和backChain两条链，更新时无锁切换避免阻塞调用。路由分为高性能的StateRouter（基于位运算）和传统Router两阶段执行
        TagStateRouter, ServiceStateRouter, AppStateRouter, StandardMeshRuleRouter
    Cluster容错策略：
        failover（失败重试），failfast(快速失败)，failsafe（失败安全），failback（失败定时重试)，forking并行调用，broadcast(广播调用)
