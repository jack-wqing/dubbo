1、域模型:
    3.0之前的版本: 只有一个作用域，通过静态变量共享
    3.0及之后的版本: 1.让Dubbo支持多应用部署
                   2.从架构上解决静态属性资源共享、清理问题
                   3.分层模型将应用的管理和服务的分开   应用: 配置中心，元数据中心

2、为什么要用到扩展
    对于一个好的框架应该遵守一定的设计规范比如设计的模式的开闭原则(扩展开发，修改关闭)
    DUBBO=RPC通信+微服务治理；微内核=核心系统【系统设计】+ 插件模块【spi】



3、Dubbo Deployer 发布器
    ApplicationDeployer用于初始化并启动应用程序实例
    ModuleDeployer模块的导出/引用服务


4、配置中心
    1.为什么需要配置中心
      集中配置管理、动态调整、自动更新、不同环境
    2.Dubbo的多配置中心: 保证其中一个配置中心集群出现不可用时能够切换成另一个配置中心集群
    分布式场景高可用: 失效转移，主备切换，降级处理

5、元数据中心
    1、元数据中心来维护RPC服务与应用的映射关系来兼容接口和应用之间的对应关系
    2、减少注册中心的负担，让注册中心更加聚焦于地址的发现和推送能力
    元数据中心并不依赖于注册中心和配置中心。用户可以自由选择是否集成和部署元数据中心



6.双注册原理
    1.ServiceDiscovery: 在注册服务时同时发布元数据，MetadataReport默认不上报
      Nacos: 1.服务注册
               2.配置注册: dataId=applicationName Group=Reversion Content=元数据内容

      通过META-INF 配置文件知道，service-discovery-registry寻找的是RegistryProtocol
                            Registry寻找的是InterfaceCompatibleRegistryProtocol

dubbo路由:
    1.普通路由: 基于静态规则或自定义条件进行路由，与服务实例的运行状态无关  // 从业务的层面
        例如: 标签路由，条件路由 脚本路由
    2.状态路由: 基于服务实例的运行状态进行动态路由  // 从服务保障的层面
        服务实例信息: 是否健康，负载情况，可用性等

    条件路由: attachment，argument，param匹配方式

Triple协议:
    参考gRPC，gRPC-Web,通用HTTP等多种协议
    目标: 对人类，开发调试友好 + 完全兼容gRPC协议 + 仅依赖标准被广泛使用的HTTP特性
    Unary请求: Http1仅支持Unary请求
    Streaming调用请求: Triple仅在支持HTTP/2上支持Streaming RPC;与gRPC协议完全一致
            Header帧 + Data帧
    规范详情: Triple协议支持同时运行在Http/1和Http/2协议之上
        1.一套自定义的精简HTTP RPC子协议，支持HTTP/1和HTTP2作为作为传输层实现，仅支持Request-Response类型的Unary RPC
        2.一套基于gRPC协议的子协议(保持和gRPC的100%兼容).仅支持HTTP/2实现，支持Unary RPC和Streaming RPC
    Triple 之 HTTP RPC协议:
        Triple HTTP RPC同时支持HTTP/1,HTTP/2作为底层传输层协议，在实现上应支持Content-Type类型为application/json, application/proto
        请求:
          i  仅支持POST请求，请求path为interfaceName/methodName,超时机制使用头:tri-service-timeout
            隔离机制: tri-service-group、tri-service-version
            TRI-Protocol-Version: 区分Triple的协议请求和其他的请求
            Message-Codec + Bare-Message: 指定消息 + 编码方式
        响应: 正确效应使用标准的http: Bare-Message就是响应体使用Content-Type+Content-Encoding响应内容
            错误响应时，返回的内容必须是Application/json
    Triple之扩展版gRPC协议
        Triple协议的Streaming请求处理完全遵循gRPC协议规范，且仅支持HTTP/2作为传输层协议；后端服务间的Unary请求默认采用扩展版gRPC协议
        Content-Type: application/grpc、application/grpc+proto、application/grpc+json, 扩展了application/triple+wrapper编码格式
        请求头: 请求头的发送在Http/2的头帧中
        响应:

Triple与gRPC的关系: 基于HTTP且完全兼容gRPC, 设计更加简单规避了gRPC官方库的问题
        实现复杂，绑定IDL,难以调试

原生多协议支持: 一个端口支持Triple gRPC和HTTP/1协议，
